Cookbook

Ship an OpenWrt package

You wrote a LuCI app or a theme. This is how to build it, prove it works on a real router, sign it, and get it somewhere people can apk add it. Copy the files, change the names, done.

The three tools

owlab

Throwaway routers in Docker. Build the package, install it, check the page loads.

owfeed

Sign the packages and write a signed inventory of a release. Or run a whole feed.

owfeed-packages

A live feed. Ask it to carry your package and users get apk upgrade.

They do not depend on each other. They agree on one thing: a directory called dist/ with one subdirectory per architecture. Anything that fills it correctly works with everything downstream.

1. Build and test it on your machine

You need Docker. Nothing else.

go install owfeed.org/owlab/cmd/owlab@latest

cd my-luci-app
owlab build --release 25.12.5      # real SDK build, writes dist/<arch>/
owlab up                            # start a router
owlab install owrt2512 dist/*/*.apk
owlab open owrt2512                 # LuCI in your browser

While you are working, skip the rebuild entirely:

owlab sync --watch    # copies your sources into the running router on every save

And the whole check in one command, which is also what CI runs:

owlab test --release 25.12.5 --release 24.10.8 \
  --install 'dist/*/luci-app-mine-*' \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'
Test both branches. 25.12 uses apk, 24.10 uses opkg, and they disagree about nearly everything. A package that works on one can fail on the other.

2. What goes where

FileWhat it is for
owlab.yamlWhich routers to spin up. Optional — flags work without it.
MakefileYour package, as OpenWrt expects. owlab build reads it.
dist/<arch>/Built packages. Produced by the build, read by everything else.
.github/workflows/ci.ymlTest on every push.
.github/workflows/release.ymlSign and publish on a tag.

A minimal owlab.yaml, if you want one:

version: 1
routers:
  - id: owrt2512
    release: "25.12.5"
  - id: owrt2410
    release: "24.10.8"
About dist/. An architecture-independent package lands in two directories, and that is correct: apk calls it noarch, opkg calls it all, and each artifact goes where it says it belongs. 
dist/
├── noarch/my-app-1.0.0-r1.apk
└── all/my-app_1.0.0-r1_all.ipk

3. GitHub Actions

.github/workflows/ci.yml

name: ci
on: [push, pull_request]
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { release: ["25.12.5", "24.10.8"] }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.3.0
      - run: owlab build --release ${{ matrix.release }}
      - uses: owfeed/owlab/action@v0.3.0
        with:
          releases: ${{ matrix.release }}
          install: dist/*/my-app-*
          assert: |
            package my-app
            http 200 /cgi-bin/luci/admin/services/mine

No keys anywhere in that job — which is what makes it safe to run on a pull request from a fork.

.github/workflows/release.yml

name: release
on:
  push: { tags: ["v*"] }
permissions: { contents: read }
jobs:
  release:
    runs-on: ubuntu-latest
    permissions: { contents: write }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.3.0
      - uses: owfeed/owfeed/setup@v0.1.5

      - run: owlab build --release 25.12.5
      - run: owlab build --release 24.10.8

      - name: Sign and write the manifest
        env: { OWFEED_RELEASE_KEY: ${{ secrets.RELEASE_KEY }} }
        run: owfeed release --repo ${{ github.repository }} --tag ${{ github.ref_name }}

      - run: gh release create "${{ github.ref_name }}" --generate-notes
             dist/*/*.apk dist/*/*.ipk dist/manifest.txt*
        env: { GH_TOKEN: ${{ github.token }} }

Make the key once and put it in the repository's secrets:

owfeed keygen --usign -o release.key
gh secret set RELEASE_KEY < release.key
git add release.key.pub && git commit -m "the public half"
Keep the public half in the repo. It is how anybody — and the feed — checks that a release is really yours. The private half never leaves the secret.

4. GitLab CI

Same three commands, different file. Both binaries are single static downloads, so there is nothing to install:

build:
  image: docker:27
  services: [docker:27-dind]
  variables: { DOCKER_HOST: tcp://docker:2375, DOCKER_TLS_CERTDIR: "" }
  script:
    - wget -qO owlab https://github.com/owfeed/owlab/releases/latest/download/owlab-linux-amd64
    - wget -qO owfeed https://github.com/owfeed/owfeed/releases/latest/download/owfeed-linux-amd64
    - chmod +x owlab owfeed && export PATH="$PWD:$PATH"
    - owlab build --release 25.12.5
    - owlab test --release 25.12.5 --install 'dist/*/my-app-*'
  artifacts:
    paths: [dist/]

release:
  needs: [build]
  rules:
    - if: $CI_COMMIT_TAG
  script:
    - wget -qO owfeed https://github.com/owfeed/owfeed/releases/latest/download/owfeed-linux-amd64
    - chmod +x owfeed
    - export OWFEED_RELEASE_KEY="$RELEASE_KEY"
    - ./owfeed release --repo "$CI_PROJECT_PATH" --tag "$CI_COMMIT_TAG"

owfeed release picks up CI_PROJECT_PATH and CI_COMMIT_TAG on its own, so the flags above are only there to be explicit.

5. Get into the feed

Now users can install your package from a release. To let them apk upgrade instead, ask owfeed-packages to carry it.

  1. Publish a release with a signed manifest. That is the owfeed release step above. The feed verifies it before touching anything.
  2. Open an issue from the Request package publication template. Fill in the repository, a tag, your public key and its id.
  3. A bot checks it within a minute — the release exists, the manifest verifies against the key you claim, the format is one the feed reads. It tells you what is wrong, if anything is.
  4. A person reviews the key. This is the only manual step and it is not skippable: adding a key is the whole trust decision.
  5. After that it is automatic. Every release you tag is picked up within the hour and lands in the feed with no further action from you.
Why the manifest matters. Publish one and updates land unattended. Publish bare files instead and every update waits for a human, because a signature over the files does not say which files a release contains.

Check it installs from the feed, not just from a file

Once you are in the feed, this is the check worth having. Installing a file proves the package works; installing it by name out of a signed index proves the channel does — that the index parses, the URL does not redirect, and the key matches:

owlab test --release 25.12.5 \
  --feed 'https://repo.owfeed.org/releases/25.12/x86_64/packages.adb' \
  --feed-key ./owfeed-packages.pem \
  --install my-app \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'

6. Already shipping on 24.10? Add 25.12

This is the common case: an .ipk that has worked for years, and users on 25.12 asking for an apk. You do not need to port anything.

owlab build --release 25.12.5     # the same Makefile, an apk out the other end
owlab test  --release 25.12.5 --install 'dist/*/my-app-*'

If it builds and the page loads, you are done — publish both from one release job, as in section 3. Two things usually need a look:

WhatWhy
conffilesEvery /etc/config/* your package ships must be declared, or an upgrade overwrites the user's settings. apk is stricter about this than opkg was.
arch: allapk rejects all as uninstallable. Use LUCI_PKGARCH:=all and let the build translate it — that is what OpenWrt's own packaging does.

If your package is a theme, an app, a script or a static binary, you do not need the SDK at all — owfeed build packages a directory that is already laid out the way it should install, in seconds rather than a toolchain download.

7. What your users do

Once you are in the feed, this is the whole instruction — and it is worth putting in your README:

# OpenWrt 25.12 and later
apk add ca-bundle libustream-mbedtls
wget https://repo.owfeed.org/owfeed-packages.pem \
  -O /etc/apk/keys/owfeed-packages.pem
echo "https://repo.owfeed.org/releases/25.12/$(cat /etc/apk/arch)/packages.adb" \
  > /etc/apk/repositories.d/owfeed-packages.list
apk update && apk add my-app
Tell them not to install the file directly. apk add ./my-app.apk writes a pin on the file's hash into /etc/apk/world, the pin survives sysupgrade, and the package then never upgrades from the feed again.
