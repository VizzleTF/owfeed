Выпустить пакет

Для тех, кто написал приложение LuCI или тему и хочет, чтобы её ставили. Пять шагов: проверить у себя, завести CI, подписать релиз, попасть в фид и закрыть старую линию релизов. Копируйте файлы и меняйте имена.

1. Проверить на живом роутере

Нужен Docker. Больше ничего.

go install owfeed.org/owlab/cmd/owlab@latest

cd my-luci-app
owlab build --release 25.12.5    # настоящая сборка в SDK, пишет в dist/<arch>/
owlab up                         # поднять роутер
owlab install owrt2512 dist/*/*.apk
owlab open owrt2512              # LuCI в браузере

Пока идёт работа, пересборку можно пропускать. sync копирует исходники в живой роутер и перезагружает LuCI:

owlab sync --watch

Вся проверка одной командой — она же крутится в CI:

owlab test --release 25.12.5 --release 24.10.8 \
  --install 'dist/*/luci-app-mine-*' \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'

Команда поднимает роутеры, ставит пакет, проверяет утверждения, всё гасит и выходит с кодом 0 или 1. Две вещи, которых не сделает curl руками: она сначала логинится в LuCI, потому что иначе любая страница admin отвечает редиректом на форму входа, и она роняет тест на ответе 200, в теле которого страница ошибки — диспетчер LuCI отдаёт 200 вместе с трейсбеком.

Проверяйте обе линии релизов. На 25.12 пакетный менеджер apk, на 24.10 opkg, и совпадают они почти ни в чём. Пакет, который работает на одной, может упасть на другой.

Минимальный owlab.yaml

Необязателен, флаги выше работают и без него. Пригодится, когда нужен один и тот же набор роутеров каждый раз:

version: 1
routers:
  - id: owrt2512
    release: "25.12.5"
  - id: owrt2410
    release: "24.10.8"

Указывайте точные номера релизов. Образы и фиды snapshot пересобираются каждый день и независимо друг от друга, поэтому установки начинают падать в течение суток.

2. Завести CI

.github/workflows/ci.yml

name: ci
on: [push, pull_request]
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { release: ["25.12.5", "24.10.8"] }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.5.1
      - run: owlab build --release ${{ matrix.release }}
      - uses: owfeed/owlab/action@v0.5.1
        with:
          releases: ${{ matrix.release }}
          install: dist/*/my-app-*
          assert: |
            package my-app
            http 200 /cgi-bin/luci/admin/services/mine

Ключей в этом job нет вообще, поэтому его безопасно гонять на pull request из форка.

GitLab CI

Те же команды, другой файл. Оба инструмента — один статический бинарь:

build:
  image: docker:27
  services: [docker:27-dind]
  variables: { DOCKER_HOST: tcp://docker:2375, DOCKER_TLS_CERTDIR: "" }
  script:
    - wget -qO- https://github.com/owfeed/owlab/releases/download/v0.5.1/owlab_0.5.1_linux_amd64.tar.gz | tar xz
    - export PATH="$PWD:$PATH"
    - owlab build --release 25.12.5
    - owlab test --release 25.12.5 --install 'dist/*/my-app-*'
  artifacts:
    paths: [dist/]

3. Подписать релиз

Ключ делается один раз, у вас на машине. Приватная половина уходит в секреты репозитория:

owfeed keygen --usign -o release.key
# пишет release.key (приватный, 0600) и release.pub (публичный), печатает id ключа

gh secret set OWFEED_RELEASE_KEY < release.key
git add release.pub && git commit -m "publish the public half"
Коммитьте публичную половину и никогда приватную. По release.pub кто угодно, включая фид, проверяет, что релиз действительно ваш. release.key в репозиторий попадать не должен: опубликованный ключ подписи отозвать нельзя. Запишите id ключа, который напечатал keygen — его спросит фид.

.github/workflows/release.yml

name: release
on:
  push: { tags: ["v*"] }
permissions: { contents: read }
jobs:
  release:
    runs-on: ubuntu-latest
    permissions: { contents: write }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.5.1
      - uses: owfeed/owfeed/setup@v0.3.3

      - run: owlab build --release 25.12.5
      - run: owlab build --release 24.10.8

      - name: Подписать пакеты и написать манифест
        env: { OWFEED_RELEASE_KEY: ${{ secrets.OWFEED_RELEASE_KEY }} }
        run: owfeed release

      - run: gh release create "${{ github.ref_name }}" --generate-notes
             dist/*/*.apk dist/*/*.ipk dist/manifest.txt*
        env: { GH_TOKEN: ${{ github.token }} }

owfeed release сам берёт репозиторий и тег из GITHUB_REPOSITORY и GITHUB_REF_NAME на GitHub, а на GitLab — из CI_PROJECT_PATH и CI_COMMIT_TAG. Флаги --repo и --tag нужны, только если хотите их переопределить.

Зачем нужен манифест

owfeed release пишет manifest.txt: каждый файл релиза, его размер и хеш, плюс репозиторий и тег, которым он принадлежит. Всё это подписано вашим ключом usign.

Репозиторий и тег записаны там потому, что подпись доказывает, кто написал документ, но никогда — о чём он. Без этих строк манифест, взятый из другого вашего релиза, отлично прошёл бы проверку как этот.

4. Попасть в фид

Сейчас пакет уже можно поставить из релиза. Чтобы у пользователей заработал apk upgrade, попросите фид взять его к себе. Например, owfeed-packages.

  1. Выпустите релиз с подписанным манифестом. Это шаг 3. Фид проверяет манифест до того, как что-либо тронет.
  2. Откройте issue по шаблону Request package publication: репозиторий, тег, ваш публичный ключ и его id.
  3. Бот проверит за минуту — что релиз существует, что манифест сходится с ключом, который вы называете своим, и что формат читаемый. Если что-то не так, он скажет что.
  4. Ключ смотрит человек. Единственный ручной шаг, и обойти его нельзя: добавление ключа и есть всё решение о доверии.
  5. Дальше автоматика. Каждый новый тег подхватывается в течение часа.

Показать это в своём README

Когда фид взял ваш пакет, он публикует для него два бейджа, и они обновляются вместе с фидом. Бейджи рисуются по только что собранному индексу, поэтому не могут показать версию, которой фид не раздаёт:

[![owfeed](https://img.shields.io/endpoint?url=https://repo.owfeed.org/badge/my-app.json)](https://owfeed.org/install/ru/)
[![owfeed](https://img.shields.io/endpoint?url=https://repo.owfeed.org/badge/my-app-releases.json)](https://owfeed.org/install/ru/)

Первый показывает версию, которую раздаёт фид; второй — линии релизов, на которых он её раздаёт.

Есть манифест — обновления приезжают без человека. Если вместо него просто файлы, каждое обновление ждёт человека: подпись на файлах не говорит, какие файлы входят в релиз.

Проверить, что ставится из фида, а не только из файла

Установка файла доказывает, что работает пакет. Установка по имени из подписанного индекса доказывает, что работает канал: индекс читается, URL не редиректит, ключ на роутере совпадает с тем, которым подписано:

owlab test --release 25.12.5 \
  --feed 'https://repo.owfeed.org/releases/25.12/x86_64/packages.adb' \
  --feed-key ./owfeed-packages.pem \
  --install my-app \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'

Здесь ничего не ставится с --allow-untrusted. Пакет принимается именно потому, что подписан индекс.

5. Уже есть пакет на 24.10? Добавьте 25.12

Портировать ничего не нужно. Тот же Makefile выдаёт apk:

owlab build --release 25.12.5
owlab test  --release 25.12.5 --install 'dist/*/my-app-*'

Собралось и страница открывается — публикуйте обе линии из одного релизного job, как в шаге 3. Обычно стоит посмотреть на две вещи:

ЧтоПочему
conffilesКаждый /etc/config/*, который везёт пакет, обязан быть объявлен. Иначе sysupgrade молча заменит настройки пользователя вашими значениями по умолчанию, и так на каждом обновлении прошивки.
arch: allapk считает all неустановимым. Пишите LUCI_PKGARCH:=all и дайте сборке перевести это — так делает и собственная упаковка OpenWrt.

Если пакет — тема, приложение, скрипт или статический бинарь, SDK не нужен вовсе. owfeed build упакует уже разложенный каталог за секунды вместо того, чтобы качать тулчейн.

Что делают пользователи

Когда пакет в фиде, вся инструкция — три команды. Положите её в свой README или дайте ссылку на страницу установки: там обе линии релизов и ошибки, из-за которых люди теряют обновления.
