Cookbook

Ship your package

For someone who wrote a LuCI app or theme and wants people to install it. Five steps: test it locally, wire up CI, sign a release, get into a feed, and cover the older release line. Copy the files and change the names.

1. Test it on a real router

You need Docker. Nothing else.

go install owfeed.org/owlab/cmd/owlab@latest

cd my-luci-app
owlab build --release 25.12.5    # real SDK build, writes dist/<arch>/
owlab up                         # start a router
owlab install owrt2512 dist/*/*.apk
owlab open owrt2512              # LuCI in your browser

While you are working, skip the rebuild entirely. sync copies your sources into the running router and reloads LuCI:

owlab sync --watch

The whole check in one command — this is also what CI runs:

owlab test --release 25.12.5 --release 24.10.8 \
  --install 'dist/*/luci-app-mine-*' \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'

It starts the routers, installs, asserts, tears down, and exits 0 or 1. Two things it does that a hand-written curl does not: it logs into LuCI first, because every admin page answers a redirect otherwise, and it fails a 200 whose body is an error page, because LuCI's dispatcher returns 200 with the traceback in it.

Test both release lines. 25.12 uses apk, 24.10 uses opkg, and they agree on almost nothing. A package that works on one can fail on the other.

A minimal owlab.yaml

Optional — the flags above work without one. It pays off once you want the same set of routers every time:

version: 1
routers:
  - id: owrt2512
    release: "25.12.5"
  - id: owrt2410
    release: "24.10.8"

Pin exact point releases. snapshot images and snapshot feeds are rebuilt daily and independently, so installs start failing within a day.

2. Wire up CI

.github/workflows/ci.yml

name: ci
on: [push, pull_request]
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { release: ["25.12.5", "24.10.8"] }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.5.1
      - run: owlab build --release ${{ matrix.release }}
      - uses: owfeed/owlab/action@v0.5.1
        with:
          releases: ${{ matrix.release }}
          install: dist/*/my-app-*
          assert: |
            package my-app
            http 200 /cgi-bin/luci/admin/services/mine

There are no keys in this job, which is what makes it safe to run on a pull request from a fork.

GitLab CI

Same commands, different file. Both tools are single static binaries:

build:
  image: docker:27
  services: [docker:27-dind]
  variables: { DOCKER_HOST: tcp://docker:2375, DOCKER_TLS_CERTDIR: "" }
  script:
    - wget -qO- https://github.com/owfeed/owlab/releases/download/v0.5.1/owlab_0.5.1_linux_amd64.tar.gz | tar xz
    - export PATH="$PWD:$PATH"
    - owlab build --release 25.12.5
    - owlab test --release 25.12.5 --install 'dist/*/my-app-*'
  artifacts:
    paths: [dist/]

3. Sign a release

Make the key once, on your machine, and put the private half in the repository's secrets:

owfeed keygen --usign -o release.key
# writes release.key (private, 0600) and release.pub (public), and prints the key id

gh secret set OWFEED_RELEASE_KEY < release.key
git add release.pub && git commit -m "publish the public half"
Commit the public half; never the private one. release.pub is how anyone — including a feed — checks that a release is really yours. Keep release.key out of the repository: a published signing key cannot be revoked. Note the key id that keygen prints; a feed will ask for it.

.github/workflows/release.yml

name: release
on:
  push: { tags: ["v*"] }
permissions: { contents: read }
jobs:
  release:
    runs-on: ubuntu-latest
    permissions: { contents: write }
    steps:
      - uses: actions/checkout@v5
      - uses: owfeed/owlab/setup@v0.5.1
      - uses: owfeed/owfeed/setup@v0.3.2

      - run: owlab build --release 25.12.5
      - run: owlab build --release 24.10.8

      - name: Sign the packages and write the manifest
        env: { OWFEED_RELEASE_KEY: ${{ secrets.OWFEED_RELEASE_KEY }} }
        run: owfeed release

      - run: gh release create "${{ github.ref_name }}" --generate-notes
             dist/*/*.apk dist/*/*.ipk dist/manifest.txt*
        env: { GH_TOKEN: ${{ github.token }} }

owfeed release reads the repository and tag from GITHUB_REPOSITORY and GITHUB_REF_NAME on GitHub, and from CI_PROJECT_PATH and CI_COMMIT_TAG on GitLab. Pass --repo and --tag only if you need to override them.

What the manifest is for

owfeed release writes manifest.txt: every file in the release, its size and its hash, plus which repository and tag it belongs to — signed with your usign key.

It records the repository and tag because a signature proves who wrote something, never what it is about. Without those lines, a manifest lifted from another of your releases would verify perfectly as this one.

4. Get into a feed

At this point users can install your package from a release. To give them apk upgrade, ask a feed to carry it — owfeed-packages is one.

  1. Publish a release with a signed manifest. That is step 3. The feed verifies it before touching anything.
  2. Open an issue from the Request package publication template: repository, a tag, your public key and its id.
  3. A bot checks it within a minute — the release exists, the manifest verifies against the key you claim, the format is one the feed reads. It says what is wrong, if anything.
  4. A person reviews the key. The only manual step, and not skippable: adding a key is the whole trust decision.
  5. After that it is automatic. Every tag you push is picked up within the hour.

Show it in your README

Once a feed carries your package it publishes two badges for it, and they update whenever the feed does. They are rendered from the index the feed just built, so they cannot claim a version it is not serving:

[![owfeed](https://img.shields.io/endpoint?url=https://repo.owfeed.org/badge/my-app.json)](https://owfeed.org/install/)
[![owfeed](https://img.shields.io/endpoint?url=https://repo.owfeed.org/badge/my-app-releases.json)](https://owfeed.org/install/)

The first shows the version the feed serves; the second, the release lines it serves it on.

Publish a manifest and updates land unattended. Publish bare files instead and every update waits for a human, because a signature over the files does not say which files a release contains.

Check that it installs from the feed, not just from a file

Installing a file proves the package works. Installing it by name out of a signed index proves the channel works — that the index parses, the URL does not redirect, and the key on the router matches the one that signed it:

owlab test --release 25.12.5 \
  --feed 'https://repo.owfeed.org/releases/25.12/x86_64/packages.adb' \
  --feed-key ./owfeed-packages.pem \
  --install my-app \
  --assert 'http 200 /cgi-bin/luci/admin/services/mine'

Nothing is installed with --allow-untrusted here. The index's signature is what makes the package acceptable.

5. Already shipping on 24.10? Add 25.12

You do not need to port anything. The same Makefile produces an apk:

owlab build --release 25.12.5
owlab test  --release 25.12.5 --install 'dist/*/my-app-*'

If it builds and the page loads, publish both lines from one release job as in step 3. Two things usually need a look:

WhatWhy
conffilesEvery /etc/config/* your package ships must be declared. Otherwise sysupgrade replaces the user's settings with your defaults, silently, on every firmware upgrade.
arch: allapk rejects all as uninstallable. Write LUCI_PKGARCH:=all and let the build translate it — that is what OpenWrt's own packaging does.

If your package is a theme, an app, a script or a static binary, you do not need the SDK at all. owfeed build packages a directory that is already laid out the way it should install, in seconds instead of a toolchain download.

What your users do

Once you are in a feed, the whole instruction is three commands — put it in your README, or link to the install page, which covers both release lines and the mistakes that cost people their upgrades.
